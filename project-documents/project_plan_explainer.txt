Phase 4 makes our database schema understandable for the LLM.

metadata_config.yaml
→ Stores human/business descriptions for our actual tables and columns.

metadata_loader.py
→ Reads the live PostgreSQL schema from schema_extractor.py and combines it with the descriptions from metadata_config.yaml.
→ Output: one clean, complete schema containing table name, column name, actual DB type, and business description.

glossary.yaml
→ Defines business terms and what they mean in SQL.
→ Example: "total sales" → SUM(orders.amount)

glossary_loader.py
→ Loads glossary.yaml into Python so the glossary can later be provided to the LLM.

Overall:
PostgreSQL → schema_extractor → live schema
                              ↓
                 metadata_loader
                    ↑          ↓
          metadata_config    merged schema
                              ↓
                       + business glossary
                              ↓
                         LLM context

The goal of Phase 4 is NOT to generate SQL yet.
It is to prepare accurate database + business context that the LLM will use in the later Text-to-SQL phase.

Phase 5 — pgvector Ingestion: In this phase, we take the useful knowledge we created in Phase 4 — database schema information, business glossary terms, and later some example questions/SQL — convert each document into an embedding (a list of numbers representing its meaning), and store those embeddings in PostgreSQL using pgvector. This is needed because later, when a user asks a question, we don't want to send the entire schema and glossary to the LLM. Instead, we convert the user's question into an embedding, search pgvector for the most similar documents, and retrieve only the relevant schema, glossary terms, and examples. For example, if the user asks "Who are the top 5 customers by spending?", pgvector can retrieve the customers, orders, order_items information and the customer spending glossary term. The LLM then uses this smaller, relevant context to generate better SQL. We will use Mistral embeddings consistently.



PHASE 6 — Schema Context Retriever

File: `src/text_to_sql/schema/retriever.py`

Working: Takes the user's natural-language question, converts it into an embedding using the same `mistral-embed` model used during ingestion, then searches the `schema_documents` table using pgvector cosine similarity (`<=>`). It returns the top-K most relevant documents from schema, glossary, and few-shot examples.

Use: This phase connects the user's question with the correct database knowledge. Instead of sending the entire database schema to the LLM, we retrieve only the most relevant context that will later be used for SQL generation.


PHASE 7 — LangGraph State Definition

Files: `src/text_to_sql/graph/__init__.py` and `src/text_to_sql/graph/state.py`

Working: Defines a shared `AgentState` using `TypedDict`. This state acts as a common data structure passed between all LangGraph nodes. It stores the user's question, retrieved schema context, ambiguity status, clarification question, generated SQL, SQL result, final answer, messages, and retry count.

Use: This phase creates the data contract for the complete Text-to-SQL workflow. Later LangGraph nodes will read information from `AgentState`, perform their task, and update the state for the next node. It keeps the workflow organized and ensures every node works with the same structure.

PHASE 7 — LangGraph State Definition

Files:
`src/text_to_sql/graph/__init__.py`
`src/text_to_sql/graph/state.py`

Why do we need LangGraph State?

Our Text-to-SQL system will have multiple steps:

User Question
      ↓
Check Ambiguity
      ↓
Retrieve Context
      ↓
Generate SQL
      ↓
Validate SQL
      ↓
Execute SQL
      ↓
Retry if needed
      ↓
Generate Final Answer

The main problem is: **how does every step share information with the next step?**

`AgentState` solves this problem.

Think of `AgentState` as a **shared memory/data container** that travels through the entire LangGraph workflow.

Each LangGraph node can:
- Read required information from the state.
- Perform its task.
- Add or update information in the state.
- Pass the updated state to the next node.

Example:

AgentState
    ↓
Ambiguity Node → updates `ambiguity_check`
    ↓
Retriever Node → updates `schema_context`
    ↓
SQL Node → updates `sql_query`
    ↓
Execution Node → updates `sql_result`
    ↓
Answer Node → updates `final_answer`

The state will contain fields such as:

`user_query` → original user question  
`messages` → conversation messages/history  
`schema_context` → relevant documents retrieved in Phase 6  
`ambiguity_check` → whether the question is ambiguous  
`clarification_question` → question to ask the user if clarification is needed  
`sql_query` → SQL generated by the LLM  
`sql_result` → result returned by PostgreSQL  
`final_answer` → final natural-language response  
`retry_count` → number of SQL generation retries  

So, **Phase 7 does not perform any AI task itself.** It defines the common structure that all future LangGraph nodes will use to communicate and share data.

In simple terms:

**Phase 6 finds the knowledge needed to answer the question.**  
**Phase 7 defines the shared state that carries that knowledge and all other workflow data through LangGraph.**

PHASE 8 — Ambiguity Detection Node

File:
`src/text_to_sql/graph/nodes/check_ambiguity.py`

Why do we need this?

Not every user question is clear enough to generate correct SQL. For example:

"Show me the best customers."

This is ambiguous because "best" could mean:
- highest spending
- most orders
- most recent customers

If we directly generate SQL, the LLM may guess the user's intention and produce the wrong query.

The Ambiguity Detection Node solves this by checking the user's question BEFORE SQL generation.

Working:

User Question
      ↓
Ambiguity Detection Node
      ↓
Mistral Small
      ↓
Structured Pydantic Output
      ↓
Clear? ──────────→ Continue to retrieval/SQL generation
      │
      ↓
Ambiguous
      ↓
Ask clarification question

The node will return four pieces of information:

`is_ambiguous` → whether the question is unclear

`ambiguity_type` → what kind of ambiguity exists, such as missing metric, missing time period, or unclear entity

`missing_slots` → the specific information missing from the question

`clarification_question` → a simple question that can be shown to the user to get the missing information

Example:

Question:
"Show me the best customers."

Output:
`is_ambiguous = true`
`ambiguity_type = "missing_metric"`
`missing_slots = ["customer ranking metric"]`
`clarification_question = "Do you want to rank customers by total spending or number of orders?"`

For a clear question:

"Show the top 5 customers by total spending."

Output:
`is_ambiguous = false`

Why use Mistral Small?

This task does not require a large/expensive model. We only need fast classification and structured output, so Mistral Small is suitable for keeping the ambiguity-checking step cheap and fast.

Use of Phase 8:

Phase 8 acts as a **quality gate before SQL generation**. It prevents the system from guessing when the user's intent is unclear and allows the system to ask for clarification first. This makes the later SQL generation more reliable.

Verification:

Run the node standalone with 3–5 questions:
- Clear questions
- Vague questions
- Questions missing important information

The goal is to confirm that the model correctly identifies ambiguity and generates sensible clarification questions.

### Phase 9 — Clarification Interrupt/Resume Node

The purpose of Phase 9 is to handle ambiguous questions interactively. In Phase 8, the ambiguity node checks whether the user's question is clear. If the question is ambiguous, Phase 9 pauses the LangGraph workflow using `interrupt()` and asks the user for the missing information instead of generating incorrect SQL.

For example:

User: "Show me the best customers."

The ambiguity node may detect:
- is_ambiguous = True
- ambiguity_type = "ranking_criteria"
- missing_slots = ["ranking metric"]
- clarification_question = "Do you want to rank customers by total spending or number of orders?"

At this point, the graph should stop and wait for the user's response.

`ask_clarification.py` will be responsible for this behavior. When `ambiguity_check` is True, the node calls `interrupt()` with the clarification question. LangGraph pauses the execution and returns control to the application/user. The user's answer is then provided back to the graph using `Command(resume=user_answer)`.

Example:

User: "Show me the best customers."
AI: "Do you want to rank customers by total spending or number of orders?"
User: "Total spending."

The resumed node receives `"Total spending"` and merges it with the original question so the new `user_query` becomes something like:

"Show me the best customers. The user clarified: Total spending."

The graph can then run the ambiguity check again. This second check is important because the user's answer may still be incomplete.

For example:

User: "Show me the best customers."
AI: "Do you want to rank them by spending or number of orders?"
User: "Spending."
AI: "Which time period do you want to consider?"
User: "This year."

Therefore, Phase 9 creates an interrupt/resume loop:

User Question
      ↓
Check Ambiguity
      ↓
Ambiguous?
   ↓ Yes
interrupt()
   ↓
Ask User
   ↓
Command(resume=user_answer)
   ↓
Merge clarification into user_query
   ↓
Check Ambiguity Again
   ↓
Still ambiguous? ── Yes ──→ interrupt() again
   ↓ No
Retrieve Context
   ↓
Generate SQL
   ↓
Validate SQL
   ↓
Execute SQL
   ↓
Generate Final Answer

The important concept is that `interrupt()` does not terminate the workflow. It pauses the current graph execution and allows it to continue later with the user's response. `Command(resume=...)` provides that response when the graph is resumed.

For Phase 9, we should therefore create `src/text_to_sql/graph/nodes/ask_clarification.py`, implement the interrupt/resume logic, and manually verify one complete pause → user response → resume → merge → ambiguity re-check flow before connecting the node to the full graph.
