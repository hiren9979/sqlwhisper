Phase 4 makes our database schema understandable for the LLM.

metadata_config.yaml
→ Stores human/business descriptions for our actual tables and columns.

metadata_loader.py
→ Reads the live PostgreSQL schema from schema_extractor.py and combines it with the descriptions from metadata_config.yaml.
→ Output: one clean, complete schema containing table name, column name, actual DB type, and business description.

glossary.yaml
→ Defines business terms and what they mean in SQL.
→ Example: "total sales" → SUM(orders.amount)

glossary_loader.py
→ Loads glossary.yaml into Python so the glossary can later be provided to the LLM.

Overall:
PostgreSQL → schema_extractor → live schema
                              ↓
                 metadata_loader
                    ↑          ↓
          metadata_config    merged schema
                              ↓
                       + business glossary
                              ↓
                         LLM context

The goal of Phase 4 is NOT to generate SQL yet.
It is to prepare accurate database + business context that the LLM will use in the later Text-to-SQL phase.

Phase 5 — pgvector Ingestion: In this phase, we take the useful knowledge we created in Phase 4 — database schema information, business glossary terms, and later some example questions/SQL — convert each document into an embedding (a list of numbers representing its meaning), and store those embeddings in PostgreSQL using pgvector. This is needed because later, when a user asks a question, we don't want to send the entire schema and glossary to the LLM. Instead, we convert the user's question into an embedding, search pgvector for the most similar documents, and retrieve only the relevant schema, glossary terms, and examples. For example, if the user asks "Who are the top 5 customers by spending?", pgvector can retrieve the customers, orders, order_items information and the customer spending glossary term. The LLM then uses this smaller, relevant context to generate better SQL. We will use Mistral embeddings consistently.



PHASE 6 — Schema Context Retriever

File: `src/text_to_sql/schema/retriever.py`

Working: Takes the user's natural-language question, converts it into an embedding using the same `mistral-embed` model used during ingestion, then searches the `schema_documents` table using pgvector cosine similarity (`<=>`). It returns the top-K most relevant documents from schema, glossary, and few-shot examples.

Use: This phase connects the user's question with the correct database knowledge. Instead of sending the entire database schema to the LLM, we retrieve only the most relevant context that will later be used for SQL generation.


PHASE 7 — LangGraph State Definition

Files: `src/text_to_sql/graph/__init__.py` and `src/text_to_sql/graph/state.py`

Working: Defines a shared `AgentState` using `TypedDict`. This state acts as a common data structure passed between all LangGraph nodes. It stores the user's question, retrieved schema context, ambiguity status, clarification question, generated SQL, SQL result, final answer, messages, and retry count.

Use: This phase creates the data contract for the complete Text-to-SQL workflow. Later LangGraph nodes will read information from `AgentState`, perform their task, and update the state for the next node. It keeps the workflow organized and ensures every node works with the same structure.

PHASE 7 — LangGraph State Definition

Files:
`src/text_to_sql/graph/__init__.py`
`src/text_to_sql/graph/state.py`

Why do we need LangGraph State?

Our Text-to-SQL system will have multiple steps:

User Question
      ↓
Check Ambiguity
      ↓
Retrieve Context
      ↓
Generate SQL
      ↓
Validate SQL
      ↓
Execute SQL
      ↓
Retry if needed
      ↓
Generate Final Answer

The main problem is: **how does every step share information with the next step?**

`AgentState` solves this problem.

Think of `AgentState` as a **shared memory/data container** that travels through the entire LangGraph workflow.

Each LangGraph node can:
- Read required information from the state.
- Perform its task.
- Add or update information in the state.
- Pass the updated state to the next node.

Example:

AgentState
    ↓
Ambiguity Node → updates `ambiguity_check`
    ↓
Retriever Node → updates `schema_context`
    ↓
SQL Node → updates `sql_query`
    ↓
Execution Node → updates `sql_result`
    ↓
Answer Node → updates `final_answer`

The state will contain fields such as:

`user_query` → original user question  
`messages` → conversation messages/history  
`schema_context` → relevant documents retrieved in Phase 6  
`ambiguity_check` → whether the question is ambiguous  
`clarification_question` → question to ask the user if clarification is needed  
`sql_query` → SQL generated by the LLM  
`sql_result` → result returned by PostgreSQL  
`final_answer` → final natural-language response  
`retry_count` → number of SQL generation retries  

So, **Phase 7 does not perform any AI task itself.** It defines the common structure that all future LangGraph nodes will use to communicate and share data.

In simple terms:

**Phase 6 finds the knowledge needed to answer the question.**  
**Phase 7 defines the shared state that carries that knowledge and all other workflow data through LangGraph.**

### Phase 9 — Clarification Interrupt/Resume Node

The purpose of Phase 9 is to handle ambiguous questions interactively. In Phase 8, the ambiguity node checks whether the user's question is clear. If the question is ambiguous, Phase 9 pauses the LangGraph workflow using `interrupt()` and asks the user for the missing information instead of generating incorrect SQL.

For example:

User: "Show me the best customers."

The ambiguity node may detect:
- is_ambiguous = True
- ambiguity_type = "ranking_criteria"
- missing_slots = ["ranking metric"]
- clarification_question = "Do you want to rank customers by total spending or number of orders?"

At this point, the graph should stop and wait for the user's response.

`ask_clarification.py` will be responsible for this behavior. When `ambiguity_check` is True, the node calls `interrupt()` with the clarification question. LangGraph pauses the execution and returns control to the application/user. The user's answer is then provided back to the graph using `Command(resume=user_answer)`.

Example:

User: "Show me the best customers."
AI: "Do you want to rank customers by total spending or number of orders?"
User: "Total spending."

The resumed node receives `"Total spending"` and merges it with the original question so the new `user_query` becomes something like:

"Show me the best customers. The user clarified: Total spending."

The graph can then run the ambiguity check again. This second check is important because the user's answer may still be incomplete.

For example:

User: "Show me the best customers."
AI: "Do you want to rank them by spending or number of orders?"
User: "Spending."
AI: "Which time period do you want to consider?"
User: "This year."

Therefore, Phase 9 creates an interrupt/resume loop:

User Question
      ↓
Check Ambiguity
      ↓
Ambiguous?
   ↓ Yes
interrupt()
   ↓
Ask User
   ↓
Command(resume=user_answer)
   ↓
Merge clarification into user_query
   ↓
Check Ambiguity Again
   ↓
Still ambiguous? ── Yes ──→ interrupt() again
   ↓ No
Retrieve Context
   ↓
Generate SQL
   ↓
Validate SQL
   ↓
Execute SQL
   ↓
Generate Final Answer

The important concept is that `interrupt()` does not terminate the workflow. It pauses the current graph execution and allows it to continue later with the user's response. `Command(resume=...)` provides that response when the graph is resumed.

For Phase 9, we should therefore create `src/text_to_sql/graph/nodes/ask_clarification.py`, implement the interrupt/resume logic, and manually verify one complete pause → user response → resume → merge → ambiguity re-check flow before connecting the node to the full graph.


### Phase 10 — SQL Generation Node

File:
`src/text_to_sql/graph/nodes/generate_sql.py`

Why do we need this?

After the user's question is clear (either originally or after clarification), we need to convert it into a valid PostgreSQL SQL query. This node takes the resolved user question and the relevant schema context (retrieved in Phase 6) to generate SQL.

Working:

Resolved User Question + Schema Context
      ↓
SQL Generation Node
      ↓
Groq LLM (llama3-70b-8192)
      ↓
SQL Query

The node uses a detailed prompt that instructs the LLM to:
- Generate PostgreSQL SQL only
- Use only the tables, columns, and relationships from the schema context
- Follow business definitions from the glossary
- Use few-shot examples as guidance
- Prefer explicit JOIN conditions
- Respect soft-delete fields when indicated
- Return exactly one SQL query

The prompt includes:
- The resolved user question
- Relevant schema and business context (tables, columns, descriptions)
- Relevant few-shot examples

Output:
`sql_query` → The generated PostgreSQL SQL query

Example:

User Question (after clarification):
"Show me sales for current month."

Schema Context:
- orders table with order_date, amount columns
- order_items table with subtotal column
- Glossary: "sales" = SUM(order_items.subtotal)

Generated SQL:
```sql
SELECT SUM(oi.subtotal) AS total_sales
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
WHERE o.order_date >= DATE_TRUNC('MONTH', CURRENT_TIMESTAMP)
  AND o.order_date < DATE_TRUNC('MONTH', CURRENT_TIMESTAMP) + INTERVAL '1 MONTH'
LIMIT 100
```

Why use Groq llama3-70b-8192?

SQL generation requires a more capable model than ambiguity detection. The model needs to understand complex schema relationships, business logic, and SQL syntax. Groq's llama3-70b-8192 provides good performance for this task.

Note on Output Parsing:

We use `StrOutputParser` to get the raw text response from the LLM, then extract the SQL from markdown code blocks if present. This avoids issues with tool calling that some models don't support well.


### Phase 11 — SQL Validation Node

File:
`src/text_to_sql/graph/nodes/validate_sql.py`

Why do we need this?

Before executing SQL against the database, we need to validate that the generated SQL is safe and correct. This prevents:
- SQL injection attacks
- Invalid table/column references
- Non-SELECT statements (we only allow SELECT for safety)
- Syntax errors

Working:

Generated SQL Query
      ↓
SQL Validation Node
      ↓
sqlglot Parser
      ↓
Validate Statement Type (SELECT only)
      ↓
Validate Tables (exist in schema)
      ↓
Validate Columns (exist in tables)
      ↓
Add LIMIT (if not present)
      ↓
Validated SQL

The node performs several validations:

1. **Statement Type Check**: Only allows SELECT statements. Rejects INSERT, UPDATE, DELETE, DROP, etc.

2. **Table Validation**: Checks that all referenced tables exist in the live database schema.

3. **Column Validation**: Checks that all referenced columns exist in their respective tables, handling table aliases correctly.

4. **Limit Addition**: Automatically adds a default LIMIT (100) if the query doesn't already have one, preventing runaway queries.

Output:
`sql_query` → The validated SQL query (with LIMIT added if needed)

Example:

Input SQL:
```sql
SELECT * FROM products WHERE is_active = TRUE
```

Validated Output:
```sql
SELECT * FROM products WHERE is_active = TRUE LIMIT 100
```

Invalid Example:

Input SQL:
```sql
SELECT * FROM nonexistent_table
```

Error:
`Unknown table(s): nonexistent_table`

Why use sqlglot?

sqlglot is a powerful SQL parser that can validate SQL syntax without executing it. It supports PostgreSQL dialect and provides detailed error messages.

### Phase 14 — LangGraph Workflow Builder

File:
`src/text_to_sql/graph/build_graph.py`

Why do we need this?

Now that we have all the individual nodes, we need to connect them into a complete workflow using LangGraph. This phase defines the graph structure, nodes, edges, and conditional routing logic.

Working:

The graph is built as follows:

```
START
  ↓
retrieve_schema (Phase 6)
  ↓
check_ambiguity (Phase 8)
  ↓
  ├─ ambiguous → ask_clarification (Phase 9)
  │                ↓
  │            check_ambiguity (loop back)
  │
  └─ clear → generate_sql (Phase 10)
              ↓
          validate_sql (Phase 11)
              ↓
          execute_sql (Phase 12)
              ↓
          ├─ error → generate_sql (retry)
          │           ↓
          │       validate_sql
          │           ↓
          │       execute_sql
          │
          └─ success → summarize_answer (Phase 13)
                        ↓
                      END
```

Conditional Routing:

1. **After Ambiguity Check** (`route_after_ambiguity`):
   - If `ambiguity_check` is True → go to `ask_clarification`
   - If `ambiguity_check` is False → go to `generate_sql`

2. **After SQL Execution** (`route_after_execution`):
   - If `sql_error` is present → go to `generate_sql` (retry)
   - If `sql_error` is empty → go to `summarize_answer`

Checkpointer:

The graph uses `MemorySaver` as a checkpointer to maintain state across interrupts (for clarification). This allows the graph to pause and resume with the same state using a `thread_id`.

**What is a Checkpointer?**

A checkpointer is a mechanism in LangGraph that saves the state of the workflow at each node execution. It acts like a "save point" system for the graph.

**Why do we need a Checkpointer?**

Without a checkpointer:
- The graph runs from start to finish in one go
- Cannot pause and wait for user input
- Cannot resume from where it left off
- No state persistence between requests

With a checkpointer:
- The graph can pause at any node (using `interrupt()`)
- State is saved at each step
- Can resume from the exact point where it paused
- Maintains conversation context across multiple API calls
- Uses `thread_id` to identify different user sessions

**How it works in our system:**

1. **Initial Request**: User sends "Show me sales"
   - Graph runs: `retrieve_schema` → `check_ambiguity` → detects ambiguity → `ask_clarification`
   - `ask_clarification` calls `interrupt("What metric would you like?")`
   - Graph pauses at this node
   - Checkpointer saves the current state (including the clarification question)

2. **API Response**: Returns clarification question to user

3. **User's Answer**: User sends "total sales amount"
   - API uses `graph.get_state(config)` with the same `thread_id`
   - Checkpointer retrieves the saved state
   - `state.next` shows the graph is paused at `ask_clarification`
   - API uses `Command(resume="total sales amount")` to resume
   - Graph continues from where it paused
   - User's answer is provided to the node
   - Graph continues: `check_clarification_relevance` → `check_ambiguity` → `generate_sql` → ...

**Key Concepts:**

- **`thread_id`**: Unique identifier for each conversation/session. The checkpointer uses this to store and retrieve state for different users.
- **`graph.get_state(config)`**: Retrieves the current state of the graph for a given thread_id.
- **`state.next`**: Shows the next node to execute (if graph is paused). If empty, graph is not paused.
- **`interrupt()`**: Pauses the graph execution at the current node and returns control to the caller.
- **`Command(resume=...)`**: Resumes a paused graph with the provided value (user's answer).

**Example Flow:**

```
Request 1: POST /api/chat
{
    "message": "Show me sales",
    "thread_id": "user-123"
}
→ Graph runs, pauses at ask_clarification
→ Checkpointer saves state
→ Response: {"status": "clarification_required", "question": "What metric?"}

Request 2: POST /api/chat
{
    "message": "total sales amount",
    "thread_id": "user-123"
}
→ graph.get_state() retrieves saved state
→ state.next shows paused at ask_clarification
→ Command(resume="total sales amount") resumes graph
→ Graph continues execution
→ Response: {"status": "completed", "answer": "..."}
```

**Types of Checkpointers:**

- **`MemorySaver`**: In-memory checkpointer (for development/testing). State is lost when the process restarts.
- **`PostgresSaver`**: PostgreSQL-based checkpointer (for production). State persists across restarts.
- **`SqliteSaver`**: SQLite-based checkpointer (for single-file persistence).

For production, you would replace `MemorySaver` with `PostgresSaver` to persist state in your database.



Output:
`graph` → A compiled LangGraph workflow ready for execution

Usage:

```python
from text_to_sql.graph.build_graph import build_graph

graph = build_graph()
config = {"configurable": {"thread_id": "user-session-123"}}
result = graph.invoke({"user_query": "Show me sales"}, config)
```

   - The user's answer is provided to the `ask_clarification` node
   - Graph continues execution
   - Returns final answer or another clarification question
